Documentary: A Peer‑to‑Peer, End‑to‑End Encrypted Chat Engine (Core in C++, UI in React Native)

Premise. The app is a decentralized messenger: no central message store, devices sync history directly with peers. The C++ core (“core”) owns identity, crypto, networking, storage, and sync. React Native (RN) renders UI and orchestrates flows through a thin bridge. The architecture is layered to add voice/video and new features without redesigning the foundations.
Launch constraint. The app must be launchable on any device without paid instances or paid APIs (no subscriptions required to run or test).

⸻

1) System Overview & Module Map

Layers
	1.	Storage (C++): SQLite for messages, contacts, sessions, device links, pre‑keys, and queued outbound packets. Encrypted at rest via OS keystore–wrapped keys.
	2.	Crypto (C++): identity (Ed25519), key agreement (X25519), AEAD (ChaCha20‑Poly1305 or AES‑GCM), HKDF, and a Signal‑style double ratchet for 1:1. Optional hybrid post‑quantum (X25519+ML‑KEM) gated by capability flags. Group chats use MLS later.
	3.	Transport Abstraction (C++): ITransport interface. Implementations:
	•	WebRTC data channels (mobile) for ICE/STUN/TURN and DTLS/SCTP reliability.
	•	QUIC (desktop/server‑class peers) for low‑latency streams over UDP.
	•	Relay (TURN‑like) as last resort; relays see only ciphertext.
	4.	Sync & Protocol (C++): session state machine, message formats, replay protection, ACKs, resends, gaps repair, compact batching, and history reconciliation.
	5.	RN Bridge: TurboModule/JSI surface to call core methods and receive events. RN holds view‑state only; durable state lives in core.

Key property: everything above Transport is transport‑agnostic. Adding video means adding a media transport that derives keys from the same session and plugs into the same identity and NAT traversal plumbing.

⸻

2) Identities, Devices, and Trust

At first run, core generates a long‑term identity keypair (Ed25519). The UserID is a hash of the public key. Devices are linked by establishing a secure channel (scan a QR with a short authentication string) and exchanging device keys (per‑device X25519/Ed25519). The user may designate one or two “home devices” to stay online and buffer for themselves—this raises availability without introducing central storage.

Key distribution uses a pre‑key bundle pattern (X3DH‑like): devices publish signed pre‑keys (one identity key + medium‑term signed pre‑keys + one‑time pre‑keys). Initiators fetch a bundle (through any metadata‑minimizing rendezvous, e.g., DHT or contact exchange), perform X25519 with the right combos, and start a double ratchet. This yields forward secrecy (compromise of long‑term keys doesn’t reveal past messages) and break‑in recovery (future messages regain secrecy after compromise). For deniability, messages are authenticated with symmetric keys derived in the ratchet rather than static signatures on ciphertexts.

Optional PQ‑hybrid: during handshake, run both X25519 and ML‑KEM; concatenate shared secrets and HKDF. For signatures, keep Ed25519 for compactness now; add ML‑DSA as an upgrade path. Capabilities advertise support; smaller devices can opt out.

⸻

3) Message Format & Low‑Level Framing

Core transports frames (binary). Each frame:

| ProtoVersion | Type | Flags | SessionID | Counter | Nonce | Ciphertext | Tag | Padding |

	•	Type: APP_MSG, ACK, SYNC_HELLO, SYNC_CHUNK, KEY_UPDATE, PONG, etc.
	•	SessionID + Counter: replay protection and ordering.
	•	Ciphertext: AEAD‑protected payload (ChaCha20‑Poly1305 or AES‑GCM) with associated data over headers.
	•	Padding: randomized to blunt traffic analysis (tunable).

An APP_MSG payload encapsulates: chat id (implicit via session), timestamp (coarse, not trusted), content type (text/file pointer/typing), and a per‑message ratchet header. For attachments, payload includes a content key ID; actual bytes are retrieved over the same P2P link or parallel streams and encrypted with an ephemeral file key (XChaCha20‑Poly1305).

⸻

4) Storage, Indices, and Sync

SQLite schema (simplified):
	•	messages(chat_id, msg_id, sender_device, ts, aead_blob, delivered, acked, index)
	•	sessions(peer_device, session_id, root_key, chain_snd, chain_rcv, counters)
	•	prekeys(id, public, secret, used)
	•	outbox(id, frame, next_retry_at, attempts)

Write path: when sending, core encrypts, appends to messages, enqueues a frame in outbox, and immediately hands it to Transport if connected. If offline, outbox drives later retries with exponential backoff.

Sync: upon connection, peers exchange SYNC_HELLO per chat with “last index” known for that chat. Missing ranges are streamed as SYNC_CHUNK batches with ACKs. To avoid O(n) scans, each chat keeps a monotonic index and a Bloom filter of recent IDs; gaps trigger targeted resends. Conflicts are impossible for immutable messages; edits/deletes (if supported) are CRDT entries layered on top.

⸻

5) NAT Traversal and Connectivity

Most devices are behind NAT/CGNAT. We rely on ICE:
	1.	Gather candidates (host, reflexive via STUN, and relayed via TURN‑like).
	2.	Exchange candidates via a rendezvous channel (DHT entry, contact‑to‑contact sharing, or any minimal signaling). The channel carries only ICE metadata and pre‑key bundle references; no message content.
	3.	Try UDP hole punching; if it fails, fall back to relayed candidates.

Relays are dumb pipes. Frames remain E2E encrypted; relays are interchangeable and can be community‑run. QUIC peers can also attempt direct NAT traversal with simultaneous open; otherwise they tunnel over the relay. Connectivity is surfaced to RN (online/direct/relayed) for user diagnostics, not for logic.

⸻

6) Security Details and Hardening
	•	RNG: use OS CSPRNG (SecRandomCopyBytes/getrandom/BCryptGenRandom). No custom RNG.
	•	Key handling: zeroize secrets on free; mlock key material where supported; store at rest under an OS keystore–wrapped master key.
	•	Constant‑time: rely on vetted crypto libs; avoid branch‑on‑secret in our code.
	•	Metadata minimization: encrypt everything beyond what routers must see; rotate connection IDs; add jitter and optional padding; coarse timestamps.
	•	Session renewal: rotate pre‑keys and perform periodic asynchronous re‑handshakes to refresh the root key.
	•	Compromise recovery: if a device is marked compromised, peers refuse its device key and require re‑link. The user can “nuke” a device from another linked device by publishing a signed revocation to contacts.
	•	Auditing: all cryptographic choices are compile‑time declared; core version and ciphersuites are visible in settings; no telemetry.

⸻

7) React Native Integration

We expose a narrow TurboModule/JSI interface:
	•	core.start(nodeConfig)
	•	core.addContact(prekeyBundle)
	•	core.send(chatId, bytes|string)
	•	core.getHistory(chatId, cursor, limit)
	•	core.linkDevice(linkCode)
	•	Event emitter: onMessage, onConnectionChange, onPeerStatus, onError.

Binary payloads cross the bridge as ArrayBuffer/Uint8Array. On Android, we compile C++ as an NDK library and bind via JNI (C++/JNI glue). On iOS, we use Objective‑C++ for the bridge. The UI is purely declarative (message lists, composer, media pickers). All persistence lives in core; RN can query, paginate, and render.

Background behavior:
	•	Android uses a foreground service + notification to keep the node reachable when requested.
	•	iOS relies on content‑less push to wake the app for brief sync (no message content ever lives on any push server; only “you have pending data” with opaque counters).

⸻

8) Extensibility: Voice/Video and New Features

Because Transport is abstract and identity/session are shared, media is an add‑on:
	•	WebRTC already provides SRTP for A/V. We derive SRTP keys from the ratchet (exporter) or use SFrame to E2E‑encrypt media on top of SFU‑like relays if we later add group calls.
	•	Capability negotiation is part of the session: each side advertises feature bits (VIDEO, FILE2GB, MLS, PQ_HYBRID, etc.).
	•	New message types are simply new Type codes; unknown types are ignored or NACKed by policy.
	•	Groups: introduce MLS sessions with per‑member epochs; message fan‑out goes P2P per member or via designated user relays, still E2E. History sync uses epoch checkpoints.

9) Minimal C++ Surface (illustrative)

struct Frame { std::vector<uint8_t> bytes; };
struct Msg { std::string chatId; std::string id; int64_t ts; std::vector<uint8_t> body; };

class ITransport {
public:
  virtual bool connect(const PeerInfo&) = 0;
  virtual bool send(const PeerId&, const Frame&) = 0;
  std::function<void(const PeerId&, Frame&&)> onReceive;
};

class Core {
public:
  void start(const NodeConfig&);
  void addContact(const PrekeyBundle&);
  void send(const std::string& chatId, std::span<const uint8_t> plaintext);
  std::vector<Msg> getHistory(const std::string& chatId, Cursor, size_t limit);
  LinkCode beginLink(); void completeLink(const LinkCode&);
};

RN calls these via a thin bridge; all heavy work stays in C++.

⸻

10) What “best encryption” means here

We don’t invent new ciphers. We combine well‑reviewed primitives with battle‑tested constructions:
	•	Ed25519 (identity), X25519 (agreement), HKDF (KDF), ChaCha20‑Poly1305 or AES‑GCM (AEAD), Signal double ratchet for 1:1 forward secrecy and deniability, MLS for scalable groups, optional hybrid PQ for future resistance. End‑to‑end means plaintext is only ever in device memory at the endpoints.

⸻

Result. This design yields a private, resilient messenger whose core is portable C++ and whose UI is RN. It works today for text/file sync over P2P with real‑world NATs, and its layers—identity, transport, ratchet, and sync—are stable foundations for voice/video and future features without compromising end‑to‑end security.
